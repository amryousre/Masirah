# Data Model: Phase 1 Core Screening

**Date**: 2026-09-11

Derived from the Key Entities section of [spec.md](./spec.md) and section 10 of the BRD, reduced to
what Phase 1 actually needs. Entities the BRD defines for later phases, such as pipeline stages,
scorecards, messages, templates and everything in billing, are deliberately absent.

## Universal rules

These apply to every table without exception.

- **Every table carries `organisation_id`.** There are no exceptions, including lookup-style tables.
  This is the tenancy decision from Q6 and it is cheaper now than in any later migration.
- **Every table has row level security enabled**, with policies restricting access to rows whose
  `organisation_id` matches the caller's organisation. Isolation is enforced in the database, not in
  application code, per NFR-07 and Principle II.
- **Identifiers are UUIDs**, generated by the database.
- **Every table carries `created_at` and `updated_at`** as timestamps with time zone.
- **Deletions of candidate personal data are real deletions**, not soft flags, because FR-076
  requires removal within 30 days.

## Entities

### organisation

The tenant root. Owns every other record.

| Field | Type | Notes |
|---|---|---|
| id | uuid | Primary key |
| name | text | Display name |
| retention_months | integer | Default 24, drives the purge in NFR-10 |
| locale | text | `ar` or `en`, the default interface language |

Phase 1 holds one organisation per pilot. Invitations and roles arrive in Phase 2 with FR-071.

### app_user

A person signed in to an organisation. Authentication is handled by Supabase Auth; this table holds
the application-level association. Named `app_user` rather than `user`, which is a reserved word in
PostgreSQL.

| Field | Type | Notes |
|---|---|---|
| id | uuid | Matches the auth user identifier |
| organisation_id | uuid | Tenant |
| email | text | |
| locale | text | Overrides the organisation default when set |

One user per organisation in Phase 1.

### job

A role being filled, holding the specification candidates are measured against.

| Field | Type | Notes |
|---|---|---|
| id | uuid | |
| organisation_id | uuid | Tenant |
| title | text | Required |
| description | text | Free text, may be the pasted source for FR-002 |
| required_skills | text[] | |
| preferred_skills | text[] | |
| minimum_experience_years | integer | Nullable |
| location | text | Nullable |
| language_requirement | text | Nullable |
| weights | jsonb | Component weights used for scoring, defaulted per organisation |

Validation: title must be non-empty. Weights must sum to a fixed total so that scores remain
comparable; a job with malformed weights cannot be saved. The weights are whole-number percentages
keyed `skills_match`, `experience_relevance`, `education`, `tenure_stability`, `language` and
`location`, one per FR-014 component, and must total 100.

### candidate

A person who applied. Phase 1 has no cross-channel deduplication, so the same person uploaded twice
produces two candidate rows. This is recorded as a known limitation in the spec.

| Field | Type | Notes |
|---|---|---|
| id | uuid | |
| organisation_id | uuid | Tenant |
| full_name | text | Extracted, user-correctable |
| email | text | Nullable; CVs without contact details are valid |
| phone | text | Nullable |
| location | text | Nullable |
| name_normalised | text | Arabic variant-folded form, for search per FR-007 |

`name_normalised` exists so that Mohamed, Mohammed, Muhammad and محمد resolve to one searchable
form. It is derived, never entered.

### cv_file

An original uploaded document, retained unchanged and always viewable per FR-012.

| Field | Type | Notes |
|---|---|---|
| id | uuid | |
| organisation_id | uuid | Tenant |
| candidate_id | uuid | Nullable until extraction identifies a person |
| job_id | uuid | The job the file was uploaded for, null when uploaded without one. Lets a job show files still being read, before extraction creates their application |
| storage_path | text | Location in Supabase Storage: a file below `organisations/{organisation_id}/cv/{id}/`, with no empty, `.` or `..` segment and no backslash. Storage refuses object keys with non-ASCII characters, so the stored file name is an ASCII form; the name the user uploaded, Arabic included, is kept in `original_filename` |
| original_filename | text | |
| mime_type | text | |
| byte_size | integer | |
| content_hash | text | SHA-256 of file bytes; the cache key for AI-03 |
| status | enum | See state transitions below |
| failure_reason | text | Populated when status is `failed` |

`content_hash` is what makes re-uploading an identical file free. A second upload of the same bytes
reuses the existing parsed profile rather than paying for inference again.

**State transitions**:

```text
queued ──▶ extracting ──▶ extracted
                │
                ├──▶ needs_review   (parsed, but confidence below threshold — FR-011)
                └──▶ failed         (unreadable, corrupt, encrypted — surfaces in the queue too)
```

No state is terminal in the sense of being unrecoverable. A file in `needs_review` or `failed` stays
visible with its original attached, because SC-006 requires that no submitted file is ever lost.

### parsed_profile

The structured extraction derived from a cv_file. Versioned so that reprocessing never destroys
earlier results or user corrections.

| Field | Type | Notes |
|---|---|---|
| id | uuid | |
| organisation_id | uuid | Tenant |
| cv_file_id | uuid | |
| version | integer | Increments per extraction run |
| is_current | boolean | Exactly one true per cv_file |
| extraction_source | enum | `native_text`, `vision_ocr`, `tesseract_ocr`, `manual` |
| confidence | numeric | Drives the `needs_review` routing |
| profile | jsonb | Name, contact, location, experience years, employment history with dates, education, skills, languages, certifications |
| field_overrides | jsonb | User corrections per FR-010, applied over `profile` |
| extracted_at | timestamptz | |

Corrections live in `field_overrides` rather than being written into `profile`. That way a later
re-extraction can improve the machine output without silently discarding what a human fixed, which
is what "corrections are retained" in FR-010 requires.

### application

Links a candidate to a specific job. Phase 1 has no configurable pipeline stages; those arrive with
FR-051 in Phase 2.

| Field | Type | Notes |
|---|---|---|
| id | uuid | |
| organisation_id | uuid | Tenant |
| candidate_id | uuid | |
| job_id | uuid | |
| decision | enum | `undecided`, `shortlisted`, `rejected` |
| decided_by | uuid | User who made the decision, null while undecided |
| decided_at | timestamptz | |

`decided_by` is not nullable once `decision` leaves `undecided`. This is how AI-07 is enforced in
data rather than only in the interface: a rejection with no human actor is not representable.

### score

An evaluation of one application. Immutable once written; rescoring creates a new row.

| Field | Type | Notes |
|---|---|---|
| id | uuid | |
| organisation_id | uuid | Tenant |
| application_id | uuid | |
| total | integer | 0 to 100 |
| components | jsonb | Skills match, experience relevance, education, tenure stability, language, location: each `{rating, evidence}` |
| justification | text | Written explanation citing evidence, in the interface language |
| summary | text | Three to five lines per FR-016 |
| model_id | text | Provider and model identity, for AI-02 |
| provider | enum | `anthropic`, `openai` |
| prompt_version | text | For AI-02 |
| input_hash | text | Fingerprint of exactly what the model received, for AI-02 |
| weights_hash | text | Part of the cache key for AI-04 |
| cost_egp | numeric | Per-CV cost tracking against NFR-13: extraction, scoring and summary in the run that produced it |
| summary_model_id, summary_provider, summary_prompt_version | text, enum, text | The summary call's identity, since the cheap tier writes the summary (AI-05); `model_id`, `provider` and `prompt_version` are the scoring call's |
| created_at | timestamptz | |

The cache key for scoring is the triple of candidate, job and weights, expressed here as
`application_id` plus `weights_hash`. Changing weights produces a new score row rather than
overwriting the old one, which keeps every past ranking reproducible.

`input_hash` covers the redacted input, meaning the text actually sent after protected attributes
were stripped. That is what makes FR-017 auditable rather than merely asserted.

### activity

An immutable audit event, required in Phase 1 because real pilot data arrives in Phase 1 under
ADR 0003.

| Field | Type | Notes |
|---|---|---|
| id | uuid | |
| organisation_id | uuid | Tenant |
| actor_id | uuid | Null for system actions |
| action | text | For example `candidate.viewed`, `candidate.exported`, `application.rejected` |
| subject_type | text | Polymorphic |
| subject_id | uuid | |
| metadata | jsonb | |
| occurred_at | timestamptz | |

No update or delete policy exists for this table. Rows are insert-only, which is what makes it an
audit trail rather than a log.

## Relationships

```text
organisation 1──N app_user
organisation 1──N job
organisation 1──N candidate
candidate    1──N cv_file
cv_file      1──N parsed_profile        (versioned; one current)
candidate    1──N application
job          1──N application
application  1──N score                 (one per weights version)
organisation 1──N activity
```

## Retention and deletion

Two obligations that only exist in Phase 1 because of the pilot data decision.

**Automatic purge (NFR-10)**: a scheduled job removes candidate personal data older than the
organisation's `retention_months`. What is purged is the personal data: candidate identity fields,
the stored original file, and the profile content. Scores and activity rows survive in aggregate
form so that the audit trail is not destroyed by retention.

**Deletion on request (FR-076)**: removes the same set within 30 days of a request, on demand rather
than on schedule. Both paths write an activity row recording what was removed and when.

Both paths are migration 0022. A member's request is a `deletion_request` row (`candidate_id`, `requested_by`, `requested_at`, `completed_at`; at most one open per candidate), written by `request_candidate_deletion` with a `candidate.deletion_requested` activity row. The worker's hourly sweep takes open requests first, then candidates whose `created_at` is older than their organisation's `retention_months`. It removes the stored originals, then clears `candidate`'s identity fields and `name_normalised`, empties `parsed_profile.profile` and `field_overrides`, renames `cv_file.original_filename` to `removed`, stamps `purged_at` on the candidate and their files, closes the request and writes a `candidate.purged` activity row with the reason and how many files went. A purged file is never reused by the content-hash cache.

Members cannot delete candidate rows, CV file rows or stored originals directly. Both paths run
server-side and remove the stored original first, so no route can leave a CV behind in storage.
